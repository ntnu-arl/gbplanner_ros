# 多传感器建图与探索增益

更新日期：2026 年 11 月 1 日。

前后两台激光雷达已接入原生 ROS 2 地图节点与局部规划器。两路 PointCloud2 分别按采集时刻查询 TF，融合到同一张地图；规划器分别计算每台传感器的信息增益，再按原版 GBPlanner 2 的规则求和、判断前沿。占据栅格和 Voxblox TSDF 两种后端均完成了两路点云接收、地图更新、局部规划及 ValidatePath 校验。

新增的 SMB 原生双雷达配置与下面的 front/rear 算法示例不同：原 SMB 的两台物理雷达共同建图，但探索增益只使用 VLP-16。这一实际配置已在 Fortress 中完成静止扫描、融合和规划器接图验收。

## SMB 原生双雷达

`sensor_profile:=upstream` 根据已锁定的 SMB `sensor_head.urdf.xacro` 接入顶部 VLP-16 与前置 OS1。VLP 为 440×16、10 Hz、360°×30°，扫描原点相对 base_link 为 `[0.23, 0, 0.6937]` m；OS1 为 440×32、10 Hz、360°×33.222°，原点为 `[0.3, -0.3, 0.476]` m，pitch 为 0.5 rad。实际 ROS TF 已核对。原双路 relay 都通往 Voxblox，源码证据、原宏与许可保存在 [SMB 来源记录](src/gbplanner_gazebo/models/smb/SOURCE.json)。

| 层次 | 当前 upstream 配置 |
| --- | --- |
| 原生扫描 | VLP 射线 0.2–131 m；OS1 射线 0.7–100 m；各保留原扫描栅格与安装姿态 |
| ROS 点云 | `points/velodyne`／`velodyne` 与 `points/os1`／`lidar_front`；分别执行严格开区间 `(0.2,130)`、`(0.7,100)` m 输出过滤，保留采集时间与有组织布局，无效位置为 NaN |
| Voxblox 融合 | `input_sensors: [velodyne, os1]`，每路独立队列及采集时刻 TF；积分范围 0.5–50 m |
| 探索增益 | 只选 `velodyne`，20 m、360°×30°、5°×5°，前沿阈值 0.05；不把 OS1 自动加入收益求和 |

`results/smb_sensors/runtime2.json` 静止验收通过，用时 13.492 s、launch 退出码 0。每路原始／适配点云各观测到 52 帧，模拟采集频率约 10 Hz。状态快照显示 VLP／OS1 分别融合 13／14 帧，共 1,796,374 个已知体素；每路启动 TF 队列丢弃 1 帧，拒绝计数为 0。规划器状态另接收 1,794,754 个体素，查询时刻不同，不能将两个数当作同一版本差额。

记录的原生前 12 对匹配点云没有命中越界过滤；独立的 `output_gate1.json` 用大小端编码 PointCloud2 直接检查适配函数，各 7 点中 3 个越界有限点转换为 XYZ NaN，其余位置与非 XYZ 字节、源时间戳保留。这个分支检查没有启动 Node 或传感器仿真，单独计入证据。

覆盖统计另取最新点云：mapper 有 1,796,489 个体素，其中超过车体 6 m 的为 1,639,134 个；accepted 地图对应为 1,794,754 和 1,637,516 个。最远体素中心距实测 base_link 约 50.285 m，区别于从传感器原点计算的 50 m 积分范围。此次没有运动、规划或 Action 请求，不能用它替代探索任务验证；此前 compact 的十轮探索结果没有重跑。

原 ROS 1 共用输入时间门控可能丢弃同时间戳的第二路帧；ROS 2 使用独立队列，这是显式适配。该场景继续使用 0.1 m TSDF，未改成原配置的 0.2 m；OS1 从 CPU ray 转为 GPU lidar，噪声施加顺序也与 Classic 插件不同，因此本配置不代表完整 ROS 1 一致性。首次 runtime1 的安装软链接路径失败保留在 [验收记录](results/smb_sensors/checkpoint.json)，修复后完成上述 runtime2。

## 点云输入与规划模型

[示例参数](src/gbplanner_local/config/multi_sensor.yaml)中有两组独立配置。地图节点的 `input_sensors` 决定订阅哪些点云；规划节点的 `sensor.names` 定义传感器模型，`planning.exploration_sensors` 从中选择参与增益计算的模型。三组名称在示例中都使用 front、rear，程序不会据此自动生成话题或 TF。

| 配置 | 作用 | 示例 |
| --- | --- | --- |
| `input_sensors` | 地图节点接收的输入源名称 | `[front, rear]` |
| `input.<name>.topic` | 输入 PointCloud2 话题 | `/front/points`、`/rear/points` |
| `input.<name>.frame` | 对应点云的预期 frame_id | `front_lidar`、`rear_lidar` |
| `sensor.min_range`、`sensor.max_range` | 地图节点共用的点云量程 | 0.1 m、6 m |
| `sensor.names` | 规划节点中可用的静态传感器模型 | `[front, rear]` |
| `planning.exploration_sensors` | 实际参与信息增益计算的模型 | `[front, rear]` |
| `sensor.<name>.range` | 规划模型的射线尺度 | 每台 3 m |
| `sensor.<name>.center_offset` | 相对机器人中心的安装偏移 | 前 `[0.2, 0, 0]` m；后 `[-0.2, 0, 0]` m |
| `sensor.<name>.rotations` | 模型的固定 yaw、pitch、roll | 前 `[0, 0, 0]`；后 `[π, 0, 0]` rad |
| `sensor.<name>.horizontal_fov`、`vertical_fov` | 规划视场角 | 每台 π、π/3 rad |
| `sensor.<name>.horizontal_resolution`、`vertical_resolution` | 规划射线角度间隔 | 每台 π/12 rad |
| `sensor.<name>.frontier_threshold` | 单传感器前沿阈值 | 每台 0.1 |

每台规划模型产生 48 条射线。地图量程 6 m 与规划射线尺度 3 m 分别服务于实测点云融合和候选视点评分，可以采用不同值。实际点云视场由传感器输入决定，地图节点不根据规划视场剪裁点云。

`input_sensors` 留空时继续订阅原来的 `points` 话题，使用 `sensor_frame`，状态中以 `legacy` 标识。规划模型列表留空时继续使用原有单传感器标量参数。显式配置单传感器与旧配置的增益和规划路径已逐值核对。

两路消息可以各自到达，每次回调独立融合。`mapper_status` 的 `input_sources` 给出每路话题、frame、接收成功数及拒绝数；`voxel_map.header.stamp` 保留刚刚融合的那帧点云的采集时间。点云必须给出自身坐标系和非零时间戳，TF 提供对应时刻的 `map ← sensor_frame`。同一解析后话题不能作为两路输入重复融合。

## 原版算法约定

多传感器增益来自固定提交 `7301b5350915cf3a4055072ad559842db37b4ca9` 的 `Rrg::computeVolumetricGainRayModel` 与 `SensorParamsBase`。原版来源、函数定位和文件 SHA-256 保存在[来源记录](src/gbplanner_local/multi_sensor_provenance.json)。

对第 i 台传感器，分别统计未知、空闲、占据体素的射线访问次数 Uᵢ、Fᵢ、Oᵢ：

```text
Gᵢ = w_unknown · Uᵢ + w_free · Fᵢ + w_occupied · Oᵢ
G_total = Σ Gᵢ
Cᵢ = (horizontal_fovᵢ / horizontal_resolutionᵢ)
     · (vertical_fovᵢ / vertical_resolutionᵢ) · rangeᵢ
frontierᵢ = (Uᵢ · map_resolution / Cᵢ ≥ thresholdᵢ)
frontier_total = frontier₁ OR frontier₂ OR ...
```

相同体素被不同射线或传感器访问时会重复计数，增益是求和而非可见体素集合的并集。前沿标志先在每个传感器内部计算，再取逻辑 OR。这样，一台朝向未知区域的窄视场传感器仍能将该视点标记为前沿。`sensor_gain` 服务返回当前里程计位姿下每台模型的统计、总增益和合并前沿标志。

模型外参沿用原版传感器的直接旋转：

```text
R_sensor = Rz(yaw) · Ry(pitch) · Rx(roll)
p_sensor = [range · cos(h), range · sin(h), range · sin(v)]
p_body = R_sensor · p_sensor + center_offset
p_world = body_position + Rz(body_yaw) · p_body
```

这里的水平分量没有乘 `cos(v)`，因此 `range` 是原版端点公式的尺度，不能把它直接理解为所有射线的相同欧氏长度。模型中的 `kCamera` 对应原版固定角度网格分支；此次双激光实验使用 `kLidar`。

传感器旋转与原版随机采样器的旋转约定不同：`sensor.<name>.rotations` 直接使用 R，`sampling.rotations` 使用 R 的逆矩阵，并且采样区域的固定旋转不跟随机器人 yaw。例如 yaw=π/2 时，传感器局部正 x 指向机体正 y，固定采样区域的局部正 x 指向世界负 y。两处参数的顺序都为 yaw、pitch、roll，但不能互换解释。

增益射线仍从机器人中心出发，安装偏移参与端点变换；这也是原版 `computeVolumetricGainRayModel` 的行为。规划模型的 `min_range` 不裁剪这条增益分支。实际点云融合则使用 TF 中的物理传感器原点，并应用地图节点的量程配置。两者的几何用途不同，文中数据分别按各自实现记录。

## 双激光静态房间实测

[multi_sensor_demo.py](src/gbplanner_local/scripts/multi_sensor_demo.py)复用房间射线求交器生成回波。场景包含地面、顶板、外墙，以及 x∈[-0.25, 0.25]、中央留有 2 m 通道的隔墙。地图范围为 10 m × 10 m × 3 m，分辨率 0.25 m；机器人碰撞盒为 0.4 m × 0.4 m × 0.4 m。

机器人中心固定在 (-2, 0, 0)，yaw 为 0。前后雷达各从自己的物理位置发射射线，只保留各自局部 x≥0 的半视场。每台发送一帧、3,276 个 XYZ 回波，先前向、后后向。地图由这两帧回波生成，随后运行一次原生局部规划。

| 指标 | 占据栅格 | Voxblox TSDF |
| --- | ---: | ---: |
| 前向扫描后已知体素 | 5,796 | 5,587 |
| 后向扫描新增已知体素 | 5,084 | 4,437 |
| 两路融合后已知体素 | 10,880 | 10,024 |
| 融合后空闲体素 | 9,052 | 5,272 |
| 融合后占据体素 | 1,828 | 4,752 |
| 前／后成功融合帧数 | 1／1 | 1／1 |
| 拒绝帧数 | 0 | 0 |
| 局部图顶点／边 | 100／787 | 7／10 |
| 采样尝试次数 | 145 | 4,000 |
| 选中路径长度 | 2.812558 m | 0.294643 m |
| ValidatePath | valid，ok | valid，ok |

两路地图快照均保留各自输入的纳秒级采集时间，具体数值在 [occupancy/summary.json](results/multi_sensor/occupancy/summary.json) 和 [voxblox/summary.json](results/multi_sensor/voxblox/summary.json)。两条路径还按 0.025 m 间隔检查连续线段，并对机器人盒体内的点检查已观察空闲空间及隔墙几何。

在起点处，信息增益随后向区域被观察而明显变化：

| 地图与阶段 | 前向增益 | 后向增益 | 总增益 | 前／后前沿 | 合并前沿 |
| --- | ---: | ---: | ---: | --- | --- |
| 占据栅格，仅前向扫描 | 1 | 934 | 935 | false／true | true |
| 占据栅格，两路融合 | 1 | 2 | 3 | false／false | false |
| TSDF，仅前向扫描 | 340 | 934 | 1,274 | true／true | true |
| TSDF，两路融合 | 340 | 346 | 686 | true／true | true |

该表使用当前起点的模型增益；路径评分还会累积沿途视点并应用距离折扣，因此不等于这张表的总增益。

TSDF 的输出空闲区域更少、占据区域更厚，单次扫描后局部图只扩展出 7 个顶点，达到 4,000 次尝试上限，最终得到 0.295 m 左右的短路径。占据栅格则穿过中央通道规划出 2.813 m 路径。这组实验说明两种后端都接通了双传感器输入和规划流程，同时显示单帧 TSDF 在该分辨率、截断距离和占据阈值下仍限制可通行区域。后续应通过连续视点更新观察路径的变化。

## 复现

运行环境为 Ubuntu 22.04 ARM64、ROS 2 Humble、GCC 11.4；进入现有开发容器的方式见[运行方法](运行方法.md)。以下命令在工程 `ros2` 目录下执行：

```bash
source /opt/ros/humble/setup.bash
colcon build --packages-up-to gbplanner_voxblox --parallel-workers 2 --cmake-args -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=ON
source install/setup.bash

ROS_DOMAIN_ID=74 ros2 run gbplanner_local multi_sensor_demo.py --start-node --backend occupancy --output results/multi_sensor/occupancy/summary.json
ROS_DOMAIN_ID=75 ros2 run gbplanner_local multi_sensor_demo.py --start-node --backend voxblox --output results/multi_sensor/voxblox/summary.json
```

脚本自动启动 [multi_sensor.launch.py](src/gbplanner_local/launch/multi_sensor.launch.py)，完成后关闭该次启动的节点。若需要接入自己的点云和里程计，可单独启动：

```bash
ROS_DOMAIN_ID=74 ros2 launch gbplanner_local multi_sensor.launch.py backend:=occupancy
```

每个结果目录保存 `summary.json`、前向地图切片 `front_map.csv`、融合地图切片 `combined_map.csv`、`path.csv` 和节点日志 `nodes.log`。CSV 地图切片位于 z=0.125 m；三维体素统计保存在 JSON。

使用 Python 3、NumPy、Matplotlib 绘图：

```bash
python3 tools/plot_multi_sensor.py --backend occupancy
python3 tools/plot_multi_sensor.py --backend voxblox
```

图像保存为对应目录下的 `multi_sensor.png` 和 `multi_sensor.pdf`，包含两次地图切片、路径、地图增量和逐传感器增益。

6 项定向 C++ 用例均已通过，覆盖安装外参及机器人中心射线原点、重叠传感器增益求和、逐传感器前沿 OR、单侧遮挡、显式单传感器兼容性及参数约束。结果见 [unit_tests.log](results/multi_sensor/unit_tests.log) 和 [unit_tests.xml](results/multi_sensor/unit_tests.xml)。这些用例与两后端静态房间实验对应本次多传感器功能。

## Bullet 双激光飞行

双激光现已接入原版 Lee 控制器和 Bullet 刚体仿真。两个雷达刚性安装在机体前后 0.2 m，后雷达朝向反转；每帧各投射 3,240 条射线，合计 6,480 条。射线从各自的实际传感器原点出发，完整机体姿态同时作用于传感器位置和朝向。点云和 TF 使用同一采集时刻，保留 25 ms 传输延迟；积分时查询该时刻的 TF。
