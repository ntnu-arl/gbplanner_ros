# ROS 2 执行管理

2026 年 10 月 25 日，新增常驻节点 gbplanner_control，将规划服务调用与 PathFollower 动作执行连接起来。代码位于 [control_node.py](src/gbplanner_local/scripts/control_node.py)。

## 来源和实现范围

上游 planner_control_interface 的 run、runPlanner、runGlobalPlanner、runHoming 和 stopPlannerCallback 将任务触发、规划服务与机器人专用 PCIManager 分开。本次保留手动／自动触发、仅预览、返航、停止、规划和执行分离的职责，改写为 ROS 2 异步服务与动作客户端。新状态机和 ROS 2 Action 传输属于本次适配；机器人专用驱动仍未迁移；通用 PCI 的路径处理和轨迹发布已迁入独立 gbplanner_execution，详见[轨迹执行](轨迹执行.md)。

局部任务将规划器返回的完整路径交给动作执行器，保留规划器已施加的遍历长度和时间限制。提前规划关闭时，执行到完整路径终点后等待新的地图观测，再重新规划；全局重新定位和返航同样执行完整路径。自动任务达到配置的成功执行次数后请求返航，空路径重试不消耗这个次数。10 月 30 日已移除初版只取前两点的简化，避免把输出插值点或地形采样点误当成一次完整探索任务。

2026 年 10 月 30 日起，普通空局部响应按原 PCI 等待 0.5 秒后重试。等待是非阻塞状态，停止、任务时间和降落处理仍可运行。Extended／Relaxed／Minimum 保持 0→1→2 的边界尝试，自动任务一轮用尽后回到该任务最初请求的边界；Exact／Point 保持指定模式。单次任务在可用尝试结束后报告 `local_path_empty`。规划器自己的四轮无前沿计数决定全局切换，`K_REPOSITIONING`、`K_HOMING` 和全局响应的 `homing` 字段传递实际决策。空全局响应且未标记返航时停止，不另发返航请求。

常驻节点依据本次服务响应处理状态，不使用跨请求异步到达的最新指标推测失败原因。早期 local→global→homing 的空路径回退已被上述逻辑替代；后文早期试验记录保留其当时含义。

本次原生检查 `tools/check_control_empty_retry.py` 用真实规划器和控制节点完成三组场景，耗时 9.05 秒：墙阻挡时按 0/1/2/0/1/2 重试，间隔 0.510–0.550 秒，等待中停止后不再重启；全已知地图四轮计数为 1/2/3/0，默认停止，开启 `planning.go_home_if_fully_explored` 后由 `K_HOMING` 完成已在家状态。单次空局部、显式空全局和显式返航亦通过，空尝试的成功循环计数始终为 0。结果见 [control_empty_retry/summary.json](results/control_empty_retry/summary.json)。该检查只用合成地图与静止里程计，没有执行运动。

10 月 31 日接通普通局部、全局和返航的执行前重连。按原 `PCIGeneral::reconnectPath` 在 0.1 m／1.5 m 分支中从实测位置连接原路线，新增连接必须经过 `ValidatePath`。规划请求、重连校验和动作提交共用截止时间；校验期间继续移动或地图更新时最多重验 3 次。预览保持原路线，手动指定顶点不重连，单点已到达逻辑保留。

控制层保存冻结的规划响应，用重连路线做预检和 `command_path` 展示；发送给原生执行器的 Action 保留完整原响应。执行器再按最新里程计连接一次并校验，避免两层分别插入当前位置。地面首点只有确实来自实测里程计才标记 `first_pose_is_observation`，后面的规划顶点仍按固定几何校验。

原生执行器通过 `execution_status.validates_remaining_path` 和 `validated_revision` 明确声明已在执行并负责剩余路径校验。控制器核对已接受 Action 的 UUID、路线代数和有效版本后，作废自己的旧预检回调并交出进度跟踪；缺少标记的外部执行器继续由控制层复查。Action 结果仍决定成功或失败。两次 0.2 m 位移后重连、真实 TSDF 首点高度差和校验交接通过原生链路，见 `results/control_reconnection/final/run3.json`（11 项、6.258 s、6 节点 exit 0）；另有预览、障碍拒绝和有限重验结果，见项目进度中的分次记录。

## 状态与控制

| 状态 | 含义 |
| --- | --- |
| IDLE | 等待触发 |
| PLANNING | 等待异步规划服务 |
| VALIDATING | 在最新接受地图中检查指令路径，随后发送动作 |
| SENDING | 等待动作目标接受 |
| EXECUTING | 等待动作结果，接收剩余航点和距离反馈 |
| WAITING_REPLAN | 空局部响应后等待 0.5 秒，再继续边界尝试或新一轮局部规划 |
| WAITING_OBSERVATION | 检查到达位置，自动重规划前还需新地图 |
| PREVIEW | 仅发布指令路径，不发送动作 |
| STOPPING | 已发取消请求，等待原动作结束 |
| STOPPED／DONE／ERROR | 已停止／任务完成／出现错误 |

停止请求使未完成规划回调失效，防止迟到响应重新启动任务。动作目标正在发送时，先等待接受结果再取消；未确认结束前不能开始新任务。执行器拒绝、动作失败、服务超时或里程计失效会终止当前自动任务并清空指令路径。

里程计检查包括坐标系、有限数值、有效四元数、接收时间和源时间戳，默认新鲜度上限 2 秒。动作完成后仍需实际位姿接近目标，不能仅凭 success=true 认为机器人已到达。默认位置容差 0.1 m，规划服务超时 10 秒、动作超时 60 秒、最多 100 次规划执行循环；参数见节点构造函数。

## 启动与接口

在已经构建并 source 的容器内执行：

```bash
# 地图、全局规划和控制节点；等待外部传感器及动作执行器
ROS_DOMAIN_ID=48 ros2 launch gbplanner_local control.launch.py
# 完整接口测试，自启规划及控制节点，测试内部提供模拟动作执行器
ROS_DOMAIN_ID=48 ros2 run gbplanner_local control_demo.py --start-node --output results/control_integration.json
```

这两种方式分别使用。control.launch.py 不启动模拟车辆，也不自动开始任务。执行型任务须有 path_follower 动作服务器；可同时启动 gbplanner_execution 的 execution.launch.py，并接入外部轨迹消费者及里程计。预览任务无需执行器。

| 接口 | 类型 | 约定 |
| --- | --- | --- |
| pci_trigger | planner_msgs/srv/PciTrigger | bound_mode=0–4；vel_max 在 0.2–1.0 m/s 内设置速度，0 或有限越界保留上次值；set_auto 选择自动或单次；not_exe_path 选择预览 |
| pci_global | planner_msgs/srv/PciGlobal | 单次全局查询；id=0 自动选前沿，id>0 指定顶点，not_check_frontier=false 时要求图中仍有前沿；ignore_time=false 可启用时间筛选；支持预览 |
| pci_homing_trigger | planner_msgs/srv/PciHomingTrigger | 空闲时返航；执行中保留最新请求，在动作和已提交续接结束后优先处理，支持预览 |
| pci_initialization_trigger | planner_msgs/srv/PciInitialization | 空闲时执行初始化；忙时合并待执行请求，完成当前动作后从新鲜位姿生成路径 |
| pci_search | planner_msgs/srv/PciSearch | 空闲时返回已校验的搜索路径；忙时锁存最新请求，当前任务结束后按优先级消费，排队响应的 path 为空 |
| pci_to_waypoint | planner_msgs/srv/PciToWaypoint | 直达请求中的航点；忙时保留最新目标，响应保持原空结构，接受和执行状态见 control_state |
| planner_control_interface/std_srvs/go_to_waypoint | std_srvs/srv/Trigger | 前往已选择的航点，经全局规划接近；忙时成功表示排队，空闲成功表示 Action 已接受 |
| pci_stop | planner_msgs/srv/PciStop | 停止自动任务并取消活跃动作；success 表示请求已接收，最终状态见 control_state |
| control_state | std_srvs/srv/Trigger | JSON 返回状态、原因、循环次数、动作次数和最近状态记录 |
| control_status | std_msgs/msg/String | 状态转换时发布同样的 JSON |
| command_path | nav_msgs/msg/Path | 当前交给执行器的路径，预览也会发布 |
| path_follower | planner_msgs/action/PathFollower | 路径目标、成功结果和剩余航点反馈；由 gbplanner_execution 或兼容外部执行器实现 |

PathFollower 增加 bound_mode、manual_path 和 vel_max 字段，分别保持本次碰撞尺寸、手动路径语义与速度。非有限速度、自动预览和非法边界枚举被拒绝，执行任务不会并行启动。pci_global 只做一次指定的全局任务，set_auto=true 明确拒绝；保留原 runGlobalPlanner 的单次行为，不静默使用该字段开启循环。执行中返航请求不抢占当前动作，待动作和已提交续接结束后优先处理。显式停止会取消当前动作并清空排队请求。

## 初版实际验证（10 月 25 日）

[control_demo.py](src/gbplanner_local/scripts/control_demo.py) 与规划、控制节点分进程运行。它在测试进程中提供模拟 PathFollower，按路径插值更新位姿、发布里程计与地图，逐段独立检查碰撞；该执行器只用于接口验证。

- 仅预览能产生路径，未发送动作。
- 自动完成 3 次局部首边动作，再完成 1 次返航动作，回到初始位置。
- 当时全已知地图触发 local → global → homing，当前位置已在 home 时正常结束；该回退策略已于 10 月 30 日替换，不代表当前行为。
- 活跃动作中接受停止，动作确实取消，自动任务没有自行恢复；并发触发被拒绝。
- 执行器拒绝与动作 abort 均进入 ERROR；用户重新触发后可完成单次路径。
- 中断里程计发布后取消动作，原因是 odometry_lost_during_execution；旧位姿不能启动新任务。

## 地图确认与路径复查

map_updates 仅在规划器完整校验快照后发布，含 map_revision、known_cells、stamp_sec、stamp_nanosec。控制器不再将原始 voxel_map 到达视为观测成功。自动局部重规划要求动作完成后版本递增、观测时间不早于完成时刻；零戳静态夹具仅用版本。

新增 planner_msgs/srv/ValidatePath 是 ROS 2 扩展，不冒充原版接口。它检查坐标系、路径大小、有限位姿、当前盒体及整段扫掠碰撞，返回 valid、reason 和地图版本。控制器在发送前及地图变化后异步检查；失败、超时或地图清空时取消活跃动作，旧查询回调随任务 epoch 失效。

control_demo.py 已覆盖无效快照不计新观测、地图重置取消、新障碍取消、停止取消和里程计丢失取消；此次记录共 4 次取消。结果在 results/control_integration.json。动态系统由 system_demo.py 验证，候选路径及每个运动子步均做独立碰撞检查。

## 直接全局目标

原版 globalPlannerCallback 保存请求，runGlobalPlanner 将 id、not_check_frontier、ignore_time 传给规划器。新增 pci_global 沿用这条请求链路，成功响应表示任务已接收，最终结果须读 control_state。支持的组合与当前 planner_global 一致；ignore_time=false 需要先启用任务时间策略，不支持的模式在入口拒绝。

显式请求未得到路径且未标记返航时进入 ERROR／explicit_global_path_empty，不自动改为返航。普通局部任务按前文的延时重试及规划器状态切换；开始下一项普通任务会清除显式全局请求。全局路径完整交给 gbplanner_execution，保留所有中间航点。

~~~bash
# 同域启动规划、控制、原生执行及外部轨迹消费者后
ros2 service call /pci_global planner_msgs/srv/PciGlobal '{bound_mode: 3, ignore_time: true, not_exe_path: true, id: 0}'
# 独立验证脚本，自行启动三个节点和测试轨迹消费者
ROS_DOMAIN_ID=62 ros2 run gbplanner_execution pci_global_demo.py --start-node --output results/pci_global_integration.json
~~~

[联调记录](results/pci_global_integration.json) 中，从真实局部图选择前沿 7，8 个原路径航点全部进入 115 点执行轨迹，原生节点完成一次全局动作和一次返航动作。逐段轨迹及实际运动子步检查碰撞，同时检查线速度与偏航速率。验证了预览不发指令、7 类不支持参数拒绝、并发拒绝、不存在目标／无前沿不误返航，以及后续普通任务仍保持原回退。该试验使用静态占据夹具和运动学消费者，未包含动力学。

## 时间返航与任务失效

control.launch.py mission:=true 同时启用规划时间策略和控制器的状态可用性门槛。控制器接收 mission_status；时间耗尽、续航失效或任务状态断流会取消活跃动作，等待原生执行节点完成 hold。局部服务的 K_HOMING 返回完整返航路径，控制器将 mode 切换为 homing，禁止首边截断和空路径继续回退。普通探索回退到全局时遵循时间约束，显式 pci_global 尊重 ignore_time。细节与验证见[任务时间与续航](任务时间与续航.md)。

## 提前规划增量

planner_trigger_lead_time 大于零时，自动局部任务在运动中从真实执行终点请求下一段。该参数控制提前请求时机，取零也执行完整局部路径。拼接期间保持 EXECUTING，同一个动作直到最后终点才成功。控制器负责触发和任务生命周期，执行器统一负责拼接后的实测进度与地图复查。详见[提前规划与连续执行](提前规划与连续执行.md)。

## 手动运动

`pci_to_waypoint` 直接执行指定航点，保留目标朝向；外部坐标系按非零消息时间 TF 转换，零时间使用最新 TF。`pci_rotate_180_trigger`（Trigger）沿用原版绝对世界偏航 π。`pci_initialization_trigger`（PciInitialization）执行初始化路径：空中为当前位置→上升→下降→世界 X 前移，地面仅世界 X 前移。距离由 `init_motion.z_takeoff/z_drop/x_forward` 设置，控制与执行节点的 robot_type 应一致。

初始化可在执行中排队，重复请求合并；返航请求优先。初始化路径在消费请求时按新鲜里程计生成，不使用排队时的旧起点。插入初始化后，可恢复原自动任务或尚未完成的局部重试边界，恢复前仍需到达位置与新的地图观测；初始化不额外消耗探索轮数。停止、错误和地图重置清理待执行请求。空闲调用的成功表示执行器接受了动作，忙时调用的成功表示请求已锁存，具体阶段见 `control_state` 的 `pending_initialization` 与 `initialization`。

这些任务使用手动 PathFollower 目标，不重新连接路径或按切线覆盖朝向，不接受探索续接。完整路径仍经过碰撞检查，结束须由外部里程计确认。原 `planner_control_interface_trigger` 是 pci_trigger 的同实现别名。

手动往返路径可能在同一位置重复经过，因此执行器保留完整固定路径进行地图复查，不使用探索路径的单向进度裁剪；地图变化时，已经走过的部分也可能导致停止。短运动学检查中转向、TF 航点、上下行初始化、地面初始化路径及两种请求速度通过，见 [manual_execution/summary.json](results/manual_execution/summary.json)。这次没有验证外部机器人驱动或轮地动力学。

## 执行中的搜索请求（2026 年 11 月 1 日）

`pci_search` 在忙碌时保留最新一条未消费请求，冻结目标、显式起点、边界模式和是否预览。`use_current_state=true` 在实际消费时读取新鲜里程计，避免使用上一段运动开始时的旧起点。新请求不会改写已经发送给执行器的路径。

消费顺序保持返航、初始化、自动／局部任务、搜索、全局、航点请求；自动探索不会被搜索队列强行关闭。已提交的续接必须完成确认，当前动作结束后也继续遵守原到达和新观测条件。停止、错误、地图重置、动作拒绝和降落清理待办槽及未接收的服务请求。

忙时的 `success=true, path=[]` 仅表示排队成功。空闲调用保留原异步语义：预览完成路径校验，执行型请求收到 Action 接受确认后，才返回成功和规划路径；它不表示已经运动到终点。`control_state` 的 `pending_search` 和 `applied_search` 可区分待办与已消费请求。

## 执行中的下一航点（2026 年 11 月 1 日）

`pci_to_waypoint`和标准`go_to_waypoint`共享一条待执行航点槽。前者直接使用请求里的位姿，后者使用经`/move_base_simple/goal`或`/global_planner/waypoint_request`选择的目标并调用全局规划器。忙时最新接受的请求覆盖旧的未消费请求，直达和全局分支可以互相覆盖；已经交给执行器的路径保持本次任务所有权。

接受时按消息时间把目标变换到世界坐标系，并保存目标位置、朝向、分支和边界模式；非零时间使用对应TF，零时间沿用最新TF。之后修改TF或重新选点不会移动已入槽的目标。请求消费时再读取新鲜里程计作为起点，不复用上一段开始时的位置，也不重新变换目标。reentrant服务只向带锁inbox投递请求，由tick统一接受和消费；状态中的`pending_waypoint`和`applied_waypoint`分别记录目标及实际消费起点、时间戳和动作计数。

航点等待返航、初始化、自动／局部、搜索及全局请求；不会为了执行航点关闭自动模式，也不会越过活跃Action或已经提交的续接确认。动作完成后沿用已有到达检查，自动任务还保留新地图观测门。显式返航消费会按既有合同清除此前排队的local触发；返航开始后新提交的local请求才会继续参与后续调度。停止、错误、地图重置、执行器拒绝和降落清除航点槽与尚未接收的inbox请求。

标准Trigger忙时返回`success=true, message=waypoint_queued`，只表示保存成功；空闲时仍等到执行器接受Action才返回`waypoint_execution_started`，不表示已到达。`PciToWaypoint`没有响应字段，仍通过`control_state/control_status`判断阶段和结果。
